## The regression review (why this doc exists)

The user's most emphatic instruction this session: GPS accuracy is the app's entire value proposition, and they can only field-test by actually going running (max 3-4×/week) — they explicitly do not want to discover bugs mid-run, both because it's hard to notice subtle problems while exercising and because a failed test also costs them a real workout. So before any field test: **eliminate every findable problem by review, not by running.**

Process used (and should be repeated for any future GPS-reliability change): my own line-by-line trace of the diff, **plus** an independently-dispatched fresh-context subagent (no prior context, deliberately adversarial) reviewing the same diff, to counter my own confirmation bias as the code's author. Reconcile both before reporting to the user.

**Round 1** (reviewing all the GPS-reliability changes above) found two real problems, both now fixed:

1. **Real distance-corruption bug** in `DistanceAccumulator` (`RunSessionStore.kt`): the jitter-suppression "frozen anchor" also fed the impossible-jump sanity check, so the longer the anchor stayed frozen (routine during slow walking), the more the jump-rejection budget widened (`maxSpeedMetersPerSecond × elapsed-time-since-anchor`) — a single bad multipath glitch fix arriving during that window could then be wrongly accepted as real distance. **Fix**: split into two fields — `anchor` (frozen reference for jitter accumulation, unchanged purpose) and a new `lastFix` (updated on every accepted fix regardless of jitter status, used *only* for the impossible-jump check, so that check's time window stays tight — always ~1 fix-interval — regardless of how long the anchor has been frozen). New regression test: `DistanceAccumulatorTest.impossibleJumpBudgetStaysTightEvenWhileAnchorIsFrozenByJitter` (verified red before the fix, green after).
2. **Crash risk** in the new GPX export: `exportTrackAsGpx()` in `RunSessionService.kt` spawns a raw background `Thread` with no exception handling around the MediaStore write — an uncaught exception on any thread kills the whole process by default, and `ContentResolver.insert()`/`openOutputStream()`/`write()` can throw (storage full, restrictive OEM scoped-storage behavior), right at the end of every session. **Fix**: wrapped the thread body in `try { ... } catch (_: Exception) {}` — export is best-effort, not worth crashing over.

**Round 2** (re-reviewing these two fixes specifically, same dual-review process) — **complete, both fixes confirmed correct, no new issues.** Both my own manual trace and the independent fresh-context subagent traced every branch of the new `accept()` logic by hand against several realistic multi-fix sequences (sustained slow walk with frozen anchor, chain break + resume, no-jitter jog case, large legitimate gaps) and independently re-derived the new test's haversine math and confirmed it genuinely requires the fix (re-checked what the old single-anchor code would have done — it would have failed). This GPS-reliability work can be treated as closed pending an actual field test.
