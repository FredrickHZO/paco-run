# Paco Run MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a Pixel 9a-focused Android app that monitors running speed at 1 Hz and plays short pace/GPS cues while the screen is off.

**Architecture:** A single Compose Activity reads preferences from DataStore and observes a process-local `RunSessionStore`. A foreground location service owns the active session, validates `Location` samples, feeds a pure Kotlin `PaceEvaluator`, and delegates short local clips to `CuePlayer`. Android-specific boundaries stay thin so threshold and timing behavior can be tested on the JVM.

**Tech Stack:** Kotlin, AGP 9 template, compile/target SDK 37, Jetpack Compose, Material 3 `1.5.0-alpha27`, Navigation Compose, Lifecycle/ViewModel, DataStore Preferences, Google Play Services Location, Media3, Kotlin Coroutines/Flow, JUnit, Compose UI Test.

**Spec:** `docs/superpowers/specs/2026-08-29-paco-run-design.md`

## Global Constraints

- Product name: `Paco Run`; application ID: `dev.fred.pacorun`.
- Target hardware: Google Pixel 9a; min SDK 35; compile and target SDK 37.
- UI copy is Italian; audio cues are exactly `Too slow`, `Too fast`, `Good pace`, `Bad GPS`, and `Good GPS`.
- Material 3 `1.5.0-alpha27` and current official AndroidX/Google libraries are allowed and preferred; Ponytail must not remove requested dependencies or expressive APIs.
- Desired location interval is 1 second with no intentional batching.
- Pace transition default: 2 consecutive reliable samples; repeat interval default: 5 seconds.
- GPS audio notifications default off; dynamic color default on.
- Persist settings only. Never persist locations, route, session speed, duration, or history.
- No account, network feature, map, backend, database, analytics, ads, or speculative statistics code.
- Every task uses TDD where behavior is non-trivial and ends in a focused commit.

- [ ] **Step 3: Define the models**

```kotlin
data class LocationSample(
    val speedKmh: Float,
    val speedAccuracyKmh: Float?,
    val reliable: Boolean,
    val elapsedRealtimeMillis: Long,
)

enum class PaceState { ACQUIRING_GPS, GPS_WEAK, TOO_SLOW, GOOD, TOO_FAST }
enum class Cue { TOO_SLOW, TOO_FAST, GOOD_PACE, BAD_GPS, GOOD_GPS }

data class PaceConfig(
    val minKmh: Float,
    val maxKmh: Float,
    val confirmationSamples: Int,
    val repeatMillis: Long,
    val gpsCuesEnabled: Boolean,
)

data class PaceResult(val state: PaceState, val speedKmh: Float?, val cue: Cue?)
```

- [ ] **Step 4: Implement one deterministic state machine**

`PaceEvaluator` must:

1. treat unreliable samples as `GPS_WEAK` without evaluating speed;
2. emit GPS transition cues once per weak/recovered episode;
3. require `confirmationSamples` consecutive candidates before changing pace state;
4. emit `TOO_SLOW`/`TOO_FAST` on confirmed entry and every `repeatMillis` thereafter;
5. emit `GOOD_PACE` once after confirmed return from slow/fast;
6. use `elapsedRealtimeMillis`, never wall-clock time.

Keep all mutable counters and timestamps private to the evaluator; expose `current: PaceResult` read-only.

- [ ] **Step 3: Implement a calibratable quality gate**

```kotlin
class LocationSampleMapper(
    private val maxAgeMillis: Long = 3_000L,
    private val maxSpeedAccuracyMps: Float = .35f,
) {
    fun map(location: Location, nowElapsedRealtimeMillis: Long): LocationSample = map(
        speedMps = location.speed,
        accuracyMps = location.takeIf { it.hasSpeedAccuracy() }?.speedAccuracyMetersPerSecond,
        ageMillis = nowElapsedRealtimeMillis -
            TimeUnit.NANOSECONDS.toMillis(location.elapsedRealtimeNanos),
    )
}
```

The primitive overload converts with `m/s * 3.6f`, rejects negative ages, ages over 3 seconds, missing speed/accuracy, non-finite values, and speed uncertainty above `.35 m/s`. Keep `.35 m/s` constructor-injectable because real Pixel 9a runs may require calibration.
